# 本次案例沉淀（2026-10）

这份记录是排查方法的来源，不是新机器的预置结论。

## 有用的观测

- EngineCore 业务结果走共享内存，通知 socket 是额外唤醒路径。即使 wait_calls 增加，busy-loop 分支也可能使 poll/recv 长期不执行。
- PP 可能通过调度和结果就绪时序改变通知路径被处理的频率；不能仅凭“开启 PP 更明显”就证明 PP 算法错误。非 PP 也要测同类条件。
- 同一个 EngineCore 有多个结果队列；某队列 poll=0 与进程内其他队列消费、释放同时出现并不矛盾。进程级 BCC 聚合不能定位到 TP0 单个 socket。
- 原生 libzmq 路径出现过 656 字节块，某个确切 AArch64 构建的返回帧文件偏移为 0x46a10；**脚本没有把它写成默认过滤条件**。它不是跨版本不变的函数地址，也不是命令元素大小。
- 0808 镜像中的现场库报告 pyzmq 27.1.0 / libzmq 4.3.5。本次观察库 SHA256 为 `e3958a58c90c2296eef68af4c24423cce9237abfe062b6f76e4d24cf368e43ce`。新现场重新查映射库，不根据镜像名字猜版本。
- 两次十分钟 BCC 挂载只观察各自新分配集合；不能计算两次之间历史队列绝对差值。要历史增量需保持同一观察器或直接记录同一结构。

## 必须避免的失误

一次画图的数据停在 11:15，而实际时间已到 14:30。服务和压测仍运行，是自写 monitor 的 `/metrics` 请求遇到 `http.client.BadStatusLine`；它只捕获 OSError，未覆盖 HTTPException，导致退出。独立 smem 仍在更新，才补回这段实测数据。

由此形成的实现：

- 新 monitor 不把 HTTP health/metrics 请求放进内存采样循环。
- 每个样本/状态有采样时间、进程身份；plot 默认拒绝过期输入。
- 监控停写不能推断服务停止；服务健康、负载进度、监控进程/文件分别验证。
- 未采到的数据不插值冒充；独立 smem 单独标明来源与扫描时间语义。
- 修复监控以追加方式恢复，不重启服务、不截断历史数据。

## 负载控制的影响

本次经历连续并发负载与 AISBench 多轮前缀负载，不可直接混为同一实验。AISBench while-loop 的换轮会生成/加载数据，可能使业务暂停；共享内存读取间隙变长，可能进入 poll，内存曲线会出现回落。是否确实因该 socket 命令被处理，要对齐 counters/BCC 而不是凭曲线猜。

长前缀多轮对话必须考虑上下文总长度。历史窗口截断、模型/量化/KV 精度、并发和 D 端图模式的变化都需要写入 manifest。不能为了让服务启动而悄悄改配置，然后把新旧内存曲线当严格对照。

本 skill 保存工具和判断方法，没有把本次“整体 USS 增长全部来自 ZMQ”写成已证明事实。
